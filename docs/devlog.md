## 2026-11-21（土）企画を決めた（コードは書いていない）

### やったこと
- ShadowFairy をいったん区切り（11/20 鈴木先生との相談）、2作目としてステルスゲームを1か月で1ループ作る
- 企画シートを作った（`企画シート.md`）。コンセプト・敵の仕組み・やらないこと・完成基準・スケジュールを決めた

### 判断と理由
- **コンセプトは「自由な潜入」、核の一文は「敵の目を盗んで、ギリギリ横をすり抜ける」**。自由は動きの種類を増やすのではなく、道とタイミングを選べることで作る（マップの置き方で作るので、4週間でも完成させられる）
- **見つかり方にゲージを使わない**。近くで見つかったのにゲージが溜まるのを待つのはおかしい。距離で反応を変える（近い＝すぐ発見、中くらい＝怪しんで寄ってくる、音＝怪しんで寄ってくる）。リアルさと緊張感にこだわりたいから。
- **怪しんだ敵は敵AIを使って回り込んで寄ってくる**。まっすぐ歩くだけの敵より、リアルで緊張感がある。
- **見つかっても終わらない**（隠れ直せる・警戒態勢になる）。捕まったら失敗。見つかって終わりではつまらないから。
- **麻酔銃（サイレンサー付き・使いすぎると壊れて音が出る）は4週目**。使うかどうかを選ぶことが自由になり、銃声が音の仕組みにつながる。参考はメタルギアソリッド。3週目の終わり（12/12）に本体ができていなければ後回しにする。
- **書き方の決まり**：2人の先生とも「決めたルールを絶対に破らない・混ぜない」と言っていた。だから先生の言葉を根拠に自分の決まりを決めた。
  - メンバ変数に `m_` を付ける：見た人が考える時間を減らすため。土台の `m_srt` などと混ぜないため
  - 長さに単位を付けない：ゲームの中はメートルだけで取り違えが起きない。時間・角度・速さだけに付ける（リーダブルコード2章を参考）
  - 改行は `std::endl`：授業はこれで教えてもらったから。出力はデバッグのログだけなので遅さは問題にならない

### 理解できていなかったこと（要復習）
- 1行の if に `{}` を付けない書き方の危なさ（あとで行を足すと、字下げでは if の中に見えても if の外になる）
- 長さに単位を付けないなら、何で分かるようにするのか（規約に書く・共通の説明を書く・モデルも1単位＝1m にそろえる）

### 次
- 1週目の1ステップ目：鈴木先生の土台を用意して、マップを読み込み、プレイヤーが歩けるところまで
- まだ決めていないこと：プロジェクトの正式な名前・名前空間・土台のどの版を使うか

- **プロジェクトのファイル名は StealthGame**：作品の名前は後で決められるように、変わらない名前にした

- **`Stage` は `GameObject` を継承した**：現場の Unreal Engine でも、壁や地形は `AActor`（ゲームに出てくる物の親）を継承している。プレイヤー・敵と同じリストに入れて、同じ呼び方で Update・Draw できる
- **名前は `Map` ではなく `Stage`**：画面に出す地図（UI）で `Map` を使うかもしれないので、名前がぶつからないように
- **`.gmdl` は git に入れない**：90MB あって、変換し直すたびに履歴が重くなる。GitHub は 100MiB を超えるファイルを入れられない。現場でも（Unreal の DDC など）作られたものは入れず、元ファイルと作り方だけを残す方式がよく使われている
- **先生の土台も、おかしければ直してよい**：作品は自分のもの。ただし自分で一から書いたコードとは分ける（自分のコードは `src/game/`、土台を直したコミットは「土台：」で始める。最初のコミット `85fb96d` と比べれば、土台のどこを直したかが全部わかる）
- **土台の名前は、自分のコードに出てくるものだけ大文字始まりにそろえる**：自分のコードの中で土台の名前だけ小文字だと見た目がそろわないし、面接で「先生のコードだから変えなかった」と言うのは印象が良くない。全部は直さない（量が多く、先生の新しい版も取り込みにくくなるから）
- **フリーカメラは専用のクラスにして、カメラだけを渡す（依存性の注入）**：シーンに余計なものを入れたくない。窓はカメラ以外を知らなくていいので、シーンを直しても窓に影響しない
- **デバッグの窓は1つにまとめる**：窓が増えると重なって探しにくい。先生の Debug Information の中に欄を並べる形にした。直すのが土台の1か所（`End` の位置）で済むから
- **欄の最初の値は、カメラの今の位置から逆算する（acos・atan2）**：欄を開いた瞬間にカメラが飛ばない。カメラの位置を変えても、数字を2か所直さなくていい
- **物のリストを回す処理は SceneBase に書いた**：リストを持っているクラスが回し方も持つ。シーンが増えても同じ処理を書かなくていい
- **初期化は `=` と `( )`。`{ }` は使わない**：見慣れていて、VS の整形でも崩れないから
- **コメントはリーダブルコードの決まりの `//` だけ**：Doxygen の形や区切り線も考えたが、現場の規約（Epic・Google）を調べると、大事なのは形より中身（なぜ・使い方）だった
- **`--optimize` で部品を減らすのはやめた**：倉庫を出しても FPS は 56.4 で、ほとんど落ちなかった。測ってから決めると決めていた
- **描き方は、今は普通、最終的には PBR**：まず画面に出すことを優先した。PBR に変えるときは、ゲームグラフィックスで習ったリニアワークフローを使って、暗い倉庫の暗さを正しく出す
- **コンピュートシェーダーは今は使わない**：敵は数体なので CPU で間に合う。使うために使わない

### 詰まったこと・解決
- PBR にしたら全体が暗かった → 光は先生の初期値のまま（強さ 1.5・環境光 0.2・露出 0）で、倉庫に合わせて決めていなかった。欄を作って決めた
- 決めた値を定数に写すとき、光の向きの Y を 0 にしてしまい、床が真っ黒になるところだった → Y が 0 だと光が真横に進むので、上を向いた床には当たらない（床の向きと光の向きが直角で、明るさ 0）。最初に決めた値に戻した
- 床に白と青の四角が出る → 名前を調べると水たまり・矢印・線の**デカール**（床に貼る、透明なところがあるシール）。透明になるはずのところが塗りつぶされている。**原因はまだわからない**（次に調べる）

### 判断と理由
- **先生の PBR をそのまま使った**：シェーダ・`CEnvironmentCube`・`DrawPbr()` はもう作品に入っていて、先生の GP23 と中身も同じだった。ShadowFairy ではリングだけ自分でシェーダを書いた（ビュー空間で計算してカメラの位置を送らなかった）が、露出もリニアワークフローもなかった。書き直すより、先生のものを使うほうが早くて確か（Less is more）
- **リニアワークフローは先生のシェーダがやっている**：`pbrPS.hlsl` で色のテクスチャを `SRGBToLinear` でまっすぐに戻し、最後に `ToDisplay`（露出 → トーンマップ → `LinearToSRGB`）で表示用に曲げている。`.gmdl` のテクスチャ 32 枚を調べると全部 `BC7_UNORM`（`_SRGB` なし）なので、GPU が勝手に戻すことはなく、二重に戻していない
- **`CEnvironmentCube` は `GameScene` が持つ**：シーンが持っていれば、あとでプレイヤーや敵を PBR にするときにも同じものを使える。露出は画面全体の明るさなので、物ごとではなくシーンが決める。先生の GP23・参考版も、同じようにシーンが決めていた
- **`CEnvironmentCube` は `unique_ptr` で持つ**：コピーできないクラスなので、`= CEnvironmentCube()` と書けない。
　 　　「宣言したら `=` で初期化」の決まりを守るため、ほかのメンバと同じく `= nullptr` にして `Init()` で作る
- **光と露出は、欄を作って決める**：定数を直す方法だと、1回試すたびにビルドと起動で約1分かかる。欄なら画面を見たまま1秒で変えられるので、何度も試して決められる
- **光の持ち主は `Renderer` のまま**：欄は `GetLight()` で読んで `SetLight()` で書き戻すだけ。`GameScene` に持たせると、`Renderer` の中と2か所になって食い違うおそれがある。
　　Free Camera の欄（カメラの持ち主はシーンで、欄は動かすだけ）と同じ形
- **欄の中だけ「色」と「強さ」を分ける**：土台の `LIGHT` は「色 × 強さ」をかけた値しか持たない。先生の `ApplyLight()` と同じく、書き戻すときにかける
- **欄は別のクラスにした**：先生の GP23 は、デバッグの窓をシーンの関数（`DebugMaterial()` など）で書いている。1クラス1仕事と、前に作った `FreeCameraDebugPanel` にそろえて、別のクラスにした
- **コミットは3つに分けた**：`GameScene` に PBR の変更と欄の変更が両方入っていたが、PBR の分だけを先にコミットした。あとで履歴を見たとき、どのコミットで何をしたかがわかるように

### 判断と理由
- **青い四角は、描く順番を変えずに `clip` で捨てた（アルファテスト）**：倉庫のデカールの透明は a が 0 か 1 だけの2択で、glTF でも `alphaMode: MASK`（しきい値で捨てる）と指定されていた。捨てれば深度も書かないので、描く順番に関係なく直る。Unity（AlphaTest）・Unreal（Masked）でも、2択の透明は同じやり方。本物の半透明（ガラスなど）が必要になったら、そのとき「不透明を先・透明をあと」に描き分ける
- **しきい値は全部の材質で 0.5**：glTF の `alphaCutoff` の決まっていないときの値。`.gmdl` には材質ごとの `alphaMode` が残らないので、材質ごとには分けられない。今のマップで a が 1 でないテクスチャは看板とフェンスの2枚だけで、どちらも `MASK` なので困らない
- **白い水たまりは、発光を 0 にせずに発光テクスチャを読んだ**：光る看板はあとで絶対に足したい（暗い倉庫の雰囲気づくり）ので、今やっておく。参考版も、発光テクスチャを読んで掛けていた
- **「発光テクスチャがあるか」の印は b8（PBR の材質）に置いた**：先生は `env_bindings.hlsl` に「PBR の追加は b7〜b9 だけを使い、`common.hlsl` には手を入れない」と書いている。この分け方を守れば、PBR 以外のシェーダ（vertexLighting など）は何も変わらないし、先生の新しい版を取り込むときにぶつかりにくい。b8 は 48 → 64 バイトに増えたが、`static_assert` が大きさを見張っている
- **印がないとどうなるか**：GPU の t5 には、前に描いた材質の発光テクスチャが残ったまま。発光テクスチャのない材質（ランプ）でそれを掛けてしまう
- **土台のファイルの中は、まわりの書き方にそろえた**（`{` を同じ行・`auto`・`// ----` の見出し・名前の大文字小文字）：先生のコードの途中に自分の決まりの書き方を混ぜると、1つのファイルに書き方が2つになって読みにくい
- **発光テクスチャも sRGB からリニアに戻す**：発光テクスチャは「色」なので、アルベド（色のテクスチャ）と同じ決まり（`ALBEDO_TEXTURE_IS_SRGB_DATA`）に従う

### 理解できていなかったこと（要復習）
- **t5 は、テクスチャを置く棚の番号**：C++ の `SetGPU(5)`（`PSSetShaderResources(5, …)`）で5番の棚に置き、シェーダの `register(t5)` で5番から取る。番号が合っていないと別のテクスチャを読む。`b3`・`b8` の `b` は定数バッファの棚。GM31「3Dモデル表示 No1」の `PSSetShaderResources(0, 1, …)` の `0` と同じもの
